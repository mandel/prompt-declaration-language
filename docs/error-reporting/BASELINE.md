## Notes per entry

**`E-CLI-001`** — PDL file does not exist  
Fixed (spec docs/error-reporting/specs/E-BOUNDARY.md). `parse_file` raises `PDLFileNotFoundError`, which is both a `PDLParseError` and a `FileNotFoundError`, so `generate` already prints it and every existing `except FileNotFoundError` around `exec_file` keeps matching. Location is capped at 1 and that is not a defect to fix later: the error is about the path itself, so there is no line, column or excerpt that could exist. Fix scores 1 on this branch because the work directory holds no other file; the near-miss branches (missing `.pdl` suffix, a close `difflib` match, a listing of the sibling `.pdl` files) score 3 and are exercised by tests/test_parse_errors.py.

**`E-CLI-002`** — PDL path is a directory  
Fixed (spec docs/error-reporting/specs/E-BOUNDARY.md). `PDLIsADirectoryError` is also an `IsADirectoryError`. Classification is on `Path.is_dir()` rather than errno, because Windows raises `PermissionError` for `open()` on a directory. `sub/` holds no `.pdl` file here, so the reply is the shape of the fix rather than a name; with one program inside it becomes `did you mean `pdl sub/main.pdl`?` and scores 3.

**`E-CLI-003`** — malformed inline YAML passed to -d  
Fixed (spec docs/error-reporting/specs/E-BOUNDARY.md). Two devices say which of the two inputs is broken, because either alone is missable: the origin token is the literal `--data`, which cannot be read as a filename, and the note says in words that the program was never read -- true, since `-d` is parsed before `generate`. Line, column, excerpt and caret all come from PyYAML's `problem_mark`, which was computed and discarded before.

**`E-CLI-004`** — malformed pdl_model_default_parameters  
Fixed (spec docs/error-reporting/specs/E-BOUNDARY.md). `validate_pdl_model_defaults` raises `PDLScopeError(PDLException, ValueError)` carrying the path, the pattern and the offending value; `main` names the origin from a membership test on each dict as it is merged, so `--data` is known rather than guessed. The two sibling shapes that produced a bare `AssertionError` (not a list, entry not a mapping) raise the same error. Location stays 1 until phase-3 item 0: the line and column of the value inside the `-d` string need a marks-recording loader, and the record already carries the path, so that upgrade is a rendering change.

**`E-CLI-005`** — python -m pdl.pdl reports success on failure

Not 3: no column, no excerpt, no caret. Nothing else about this entry moved -- the defect is the exit code, not the diagnostic.

**`E-CODE-001`** — Python exception inside a code block  
Fixed (spec docs/error-reporting/specs/E-CODE-001.md). `call_python` renders its own diagnostic and raises a module-private `_CodeBlockRaised`, re-raised on the block's `code` key so the line is 2 rather than 0 and the `Python Code error:` category label is gone. The traceback is replaced by the frames whose *code object* came out of this block's `compile` -- the block's own code, including functions it defined -- printed with the source line the interpreter is holding (`linecache` cannot resolve `<code-block>`, which is why the old output showed no source) and a caret from CPython's position table. The test is code-object identity, not the filename this first shipped with: every block compiles under the shared name `<code-block>`, so a filename filter let a function defined in one block and called from another (the `PDL_SESSION` idiom, used by `examples/rag/tfidf_rag.pdl`) put the *other* block's line numbers into this block's source, printing an innocent line of the wrong block under a caret. Frames from another block are named in a `note:` instead. The gutter's numbering caveat is a `note:` too, emitted last among the notes and only when a gutter was printed: the rule paragraph states the rule, and a side-fact about how to read the evidence takes the same shape here as `print(...) writes to stdout` does in E-CODE-002, which is what makes the two siblings look like one tool. Making the filename unique per execution would fix that too, and was rejected: the name is readable from a succeeding program via `traceback.format_exc()`, so it is success-path output and must not move. The excerpt is lstripped and rebased like CPython's own traceback, windowed to 66 characters around the caret, and the builder is total -- an exception whose `__str__` raises degrades the message rather than replacing it with PDL's own error at `:0`. Fix scores 0 deliberately: there is nothing true and useful to say to someone who divided by zero, and the rubric ranks a vacuous `help:` below none; the NameError and ModuleNotFoundError branches of the same diagnostic do carry a checked suggestion and want corpus entries of their own. **Location still scores 1 after phase-3 item 7**, which added `  in code` to this golden: a block path does not lift an entry whose *line* is coarse, and `prog.pdl:2` is still the enclosing `code:` key while the offending statement is on file line 3. The path is coarse in the same way and for the same reason -- `code` is that same enclosing key. Rendering the column (foundation work left undone on purpose, see `get_loc_string`) would not help either; what this entry needs is the file line of the statement, which means mapping `code:N` gutter rows back onto file lines.

**`E-CODE-002`** — code block never assigns result (issue #386)  
Fixed (spec docs/error-reporting/specs/E-CODE-002.md). `call_python` reads `result` with `hasattr`/`getattr` and raises a module-private `_MissingResultError`, re-raised on the block's `code` key so the line is 2 rather than 0. The message names the `result` contract, reports what the code did bind, and computes the fix from the code's own AST -- here, the single top-level `print('hi')` becomes `result = 'hi'`. **Location still scores 1 after phase-3 item 7**, which added `  in code` to this golden: the line is still the enclosing `code:` key and the path is that same key, so neither names the offending element. Unlike E-CODE-001 there is no single offending statement to point at -- the fault is that the block as a whole bound nothing -- so `code:` is arguably the right target and the remaining point is the column, not the line.

**`E-CODE-005`** — a `lang: pdl` block whose program does not parse  
The inner diagnostic is the *whole* E-PARSE-001 diagnostic -- headline, excerpt, two carets, rule, help -- which scores 15 when it arrives on its own. Here `process_call_code` catches it and interpolates `repr(exc)` into `PDL Code error:`, so every newline becomes a literal `\n` and the whole document arrives as one line of Python list repr. That is the E-CODE-005 defect and every score below is capped by it: hygiene 1 for the repr chain, and what/why/fix held at 2 because the content is all present but has to be unescaped by eye. Location stays 1 after phase-3 item 7, which added `  in text[0]`: the outer `prog.pdl:3` is the enclosing block, right but coarse -- the failure is four lines further down, inside the nested program -- and a path naming that same enclosing block does not make it finer. The inner location names the nested source: it reads `<program:prog.pdl#text[0].code>:4:1`, where before the naming decision of INVENTORY 7.7 it read `<program>:4:1` -- the same label a top-level string program uses, with nothing to say which `code:` field the failure was in. This entry exists to pin that name, because it is the one place a CLI user sees it. Note that the outer `  in text[0]` and the `#text[0].code` inside that name are the same path in the same syntax, which is the point of `join_path` being shared.

**`E-CODE-006`** — Exception raised inside a function another `code:` block defined  
Pins a fix rather than exposing a defect: the two-`code:`-block shape that `88174ff` repaired, which the corpus could not have caught because `E-CODE-001`'s reproducer is a single block. The idiom is real, not synthetic -- `examples/rag/tfidf_rag.pdl` defines `PDL_SESSION.embed` in one block and calls it from another, which is exactly what this program does. What the golden demonstrates: the failing block's own line is rendered as source under a caret (`code:3 | result = PDL_SESSION.embed(key)`), and the frame belonging to the *other* block is named in prose (`note: raised inside \`embed\`, line 2 of another \`code:\` block, which this block called.`) instead of being indexed into this block's source. Line 2 of the *defining* block is `return 1 / 0`; line 2 of the *failing* block is `other = key.upper()`, and that line is what the regression printed under a caret labelled `in embed` -- a confidently-stated wrong location, which the rubric ranks below no location at all. Verified rather than assumed: this exact `prog.pdl`, run against `88174ff~1` (`b6d15ec`) with that tree's `src` first on `sys.path`, prints the extra gutter row `code:2 | other = key.upper()` / `^^^^^ in embed`; against HEAD it does not. `other = key.upper()` exists in the reproducer for no other reason than to be that wrong line, so a reintroduced regression has something legible to get wrong. Mechanism of the fix, in `_raised_elsewhere_note` (`pdl_interpreter.py`, around `:3352`): frames are selected by *code-object identity* against this block's `compile` result, not by filename, because every block compiles under the one shared name `<code-block>` -- a filename filter cannot tell two blocks apart. A frame that carries that filename but not this block's code object is therefore known to belong to some other block, and its line number is a coordinate in source this diagnostic does not hold, so it is described instead of quoted. Making the filename unique per execution would also work and was rejected: the name is readable from a succeeding program through `traceback.format_exc()`, so it is success-path output. Scores are identical to `E-CODE-001` because it is the same renderer: What 3 and Why 3 for naming the construct, the rule, the offending expression and where inside it control was; Fix 0 because there is nothing true and useful to say to someone who divided by zero, and the rubric ranks a vacuous `help:` below none. **Location stays 1 after phase-3 item 7**, which added `  in text[1].code` to this golden: `prog.pdl:9` is still the enclosing `code:` key of the second block while the offending statement is on file line 12 -- coarse, not wrong, and not credited as an accident since the block spans four file lines. The path does buy something short of a point: `text[1]` says *which* of the two blocks, which is the question this reproducer exists to ask, where before only the line answered it. The one gap this shape adds over `E-CODE-001` is that the other block cannot be named or located at all -- the prose note says `another \`code:\` block` because the compile-time filename is shared, so a reader with ten `code:` blocks still has to find the right one by searching for the function name.

**`E-RUNTIME-011`** — Retry succeeds on the second attempt and prints a traceback anyway (exit 0)  
The only traceback leak in the corpus that fires on a **success path**.
